# RFC 2119 severity normalization

Use RFC 2119 terms to normalize requirement and permission language only when that improves clarity in normative or behavior-defining text.

Primary source: 'https://datatracker.ietf.org/doc/html/rfc2119'

## Use this file only for these text types

Load this reference when the source is genuinely normative, such as:

- procedures
- policy
- interface contracts
- governance text
- requirements
- behavior-defining prompts or agent instructions

Do not load it for ordinary prose just because the text sounds serious.

## When not to apply this

Do not apply it mechanically to:

- quoted source text the user wants preserved
- legal text that must stay exact
- code, commands, file paths, identifiers, logs, or errors
- persuasive prose, status updates, support replies, or general documentation unless they are actually defining obligations or permissions
- prose where rhetorical voice matters more than formal obligation

## Preferred RFC 2119 terms

Use the RFC terms that match the actual obligation level:

- **MUST** / **REQUIRED** — absolute requirement
- **MUST NOT** — absolute prohibition
- **SHOULD** / **RECOMMENDED** — strong recommendation with possible valid exceptions
- **SHOULD NOT** — strong recommendation against, with possible valid exceptions
- **MAY** / **OPTIONAL** — permitted, discretionary behavior

## Normalization guidance

Translate severity labels into obligation language.

Examples:

- `critical` instruction → `MUST` or `REQUIRED`
- `important` recommendation → `SHOULD` or `RECOMMENDED`
- `optional` step → `MAY` or `OPTIONAL`

Choose the term that matches the truth of the source. Do not use a stronger modal only to sound clearer.

## Editing rule

When rewriting normative or behavior-bearing prose, replace severity labels like `CRITICAL` or `IMPORTANT` with the matching RFC 2119 term unless the text must stay exact.

Prefer obligation language over emphasis language when the goal is operational clarity.

## Audit rule

When auditing, flag severity words that hide whether the statement is a requirement, recommendation, permission, or prohibition. Suggest the matching RFC 2119 term only when it improves clarity without changing the author's meaning.
