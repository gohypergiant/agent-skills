# RFC 2119 severity normalization

Use RFC 2119 terms to express obligation and permission in behavior-defining prose.

Primary source: `https://datatracker.ietf.org/doc/html/rfc2119`

## When to apply this

Consider this normalization when editing or auditing skill prose, agent instructions, workflow guidance, guardrails, or other behavior-bearing text that uses informal severity labels such as `critical`, `important`, `mandatory`, or `optional`, and only when the source already makes the obligation level explicit enough to preserve exactly.

Do not apply it mechanically to:

- quoted source text the user wants preserved
- exact tokens, labels, or examples that define external interfaces
- logs, errors, code, commands, file paths, or identifiers

## Preferred RFC 2119 terms

Use the RFC terms that match the actual obligation level:

- **MUST** / **REQUIRED** — absolute requirement
- **MUST NOT** — absolute prohibition
- **SHOULD** / **RECOMMENDED** — strong recommendation with possible valid exceptions
- **SHOULD NOT** — strong recommendation against, with possible valid exceptions
- **MAY** / **OPTIONAL** — permitted, discretionary behavior

## Normalization guidance

Translate rhetorical severity into obligation language only when the source already makes the underlying obligation level explicit enough to preserve exactly.

Examples:

- `critical` requirement → `MUST` or `REQUIRED`
- `important` guidance → `SHOULD` or `RECOMMENDED`
- `optional` step → `MAY` or `OPTIONAL`
- `never` prohibition → usually `MUST NOT` when the rule is meant as a formal hard stop

Apply this to headings, labels, banners, and inline callouts too, not only sentence-level prose. If a heading says `MANDATORY CHECKPOINT`, `CRITICAL STEP`, or `IMPORTANT`, treat that label as behavior-defining severity language unless it is an exact token that must stay unchanged.

Choose the term that matches behavior. Do not strengthen or weaken the source rule by accident.

## Editing rule

If a user asks for behavior-preserving cleanup and the source uses severity labels like `CRITICAL`, `IMPORTANT`, or `MANDATORY`, rewrite them into RFC 2119 terms only when the source already makes the obligation level explicit enough to preserve exactly.

Do not preserve a rhetorical severity label by default just because it appears in a heading or banner. Normalize it only when doing so is strictly source-supported. If normalization would require inference or could strengthen or weaken the rule, preserve the original label and flag the ambiguity instead.

Do not normalize mechanically or just to make the prose sound more formal. If you decide to preserve the original severity label, be ready to justify that decision explicitly in terms of exactness constraints rather than style preference.

Prefer obligation language over theatrical severity labels when the text is genuinely normative. `CRITICAL` tells the reader how loudly to feel the rule. `MUST` tells the reader what level of compliance the rule requires. Never infer requirement level from rhetorical emphasis alone.

## Audit rule

When auditing, flag informal severity words if they obscure whether the text is a requirement, recommendation, permission, or prohibition. Suggest the matching RFC 2119 term only when the source already implies that obligation level and the current wording obscures it.
